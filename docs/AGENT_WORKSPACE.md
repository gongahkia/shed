Use the command palette's **AI: Complete**, **AI: Edit Selection**, **AI: Ask/Search**, and **AI: Run Task** actions, or open the panel through **View > AI Assistant**. `:agent ask`, `:agent edit`, and `:agent run` choose an action directly; `:help agent` explains setup and review. Ask/search displays a plain answer and code references. Select a reference and press Enter or **Open location** to navigate. Replies do not switch tabs or move focus. **Cancel turn** cancels preparation or a running action; only complete successful replies become proposals. Cancellation is tied to the originating action, so a delayed callback cannot cancel its successor. Connection settings scroll in short docks, keeping authentication and permission controls reachable.

Focused actions collect reply text separately from the bounded activity transcript and reject oversized answers rather than applying truncated code. The actual instruction is displayed in activity; internal prompt/context JSON is not echoed there. Selection and Ask/search reject agent filesystem writes through ACP and restrict permission approvals to reads/searches.

No baseline, ambiguous text, overlapping changes or a stale file prevents the whole proposal; there is no partial silent application. Creates require absent destinations, and rename/delete use the existing resource transaction and undo. Answers may propose up to 32 files within the 65,536-character reply limit. No-change answers display their explanation. Larger tasks require smaller requests/workspace scope. ## Architecture

Core workspace queries, edits, context, sessions and validation must remain independent of `Texteditor` and feature controllers. Swing adapters capture or mutate editor state on the EDT. Disk/process work runs off the EDT. Human UI, ACP and CLI/MCP adapters consume the same contracts; machine requests must not call ex commands that implicitly select a buffer or open a dialog.

Workspace identities resolve filesystem aliases. Document versions are opaque preconditions, and every request names its workspace/document rather than depending on the active tab. Disk results and unsaved editor results have different provenance. Wire requests are bounded and strictly decoded; errors carry stable codes, not stack traces or parsed display strings.

The existing LSP workspace-edit transaction, immutable text snapshots, workspace index, process cancellation, tasks/tests and Git services provide reusable foundations. Their migration is incremental; separate agent implementations of file writes and validation are not acceptable completion substitutes.

- Malformed/oversized messages fail deterministically; unsupported operations have structured errors.

- Read-only denies mutations/execution; background-only defers foreground operations even when otherwise permitted.
- Protected paths include README.md and Git administration, including alias/path traversal attempts.
- Unsaved contents and their versions are visible without saving; ordinary file queries do not start GUI, network or project processes.
- Reviewed changes preserve encoding/EOL and unrelated human edits; retry/cancellation cannot duplicate changes.
- Tests validate the intended snapshot, and their results become stale after changes.
- Restart, protocol failure, task cancellation and partial application retain enough state to explain and recover work.
- End-to-end fixtures cover session → context → proposal → review → validation → integration and an interrupted/resumed task. They remain headless while the no-app-launch constraint applies.

## Current workspace query CLI

`shed --workspace-api --root <directory> --stdio` serves one UTF-8 JSON-RPC 2.0 object per line. `--request '<JSON>'` instead serves one request and exits. The entry point forces headless AWT and never constructs the editor. The default disk-only mode creates no workspace files, child processes, network connections or windows and reports `editorConnected=false`. Explicit `--connect <descriptor>` instead authenticates to the selected live editor as described below.

Start with `{"jsonrpc":"2.0","id":1,"method":"workspace/info","params":{"schemaVersion":1}}`. The result identifies the canonical workspace, capabilities and implemented operations. `documents/list` and `documents/read` require that exact `workspaceId`. Read parameters are `document` (ID, local path or file URI), optional `expectedVersion`, zero-based UTF-16 `offset`, and a `limit` of at most 65,536 code units. Reads preserve complete grapheme clusters and return `nextOffset` plus `truncated`. Document metadata distinguishes editor/disk provenance, dirty state, completeness, encoding, byte-order mark and original newline style. Partial large-file editor projections are reported rather than misrepresented as complete documents.

Requests are bounded to 1 MiB and 64 levels of JSON nesting. Duplicate keys, malformed UTF-8/JSON, ambiguous numeric limits and unsupported fields fail explicitly. Git administration, excluded paths, root escapes and unresolved aliases are rejected. The disk-only adapter advertises `workspace/info`, `documents/list`, `documents/read`, `files/list` and `search/text`. Connected adapters additionally advertise permitted proposal operations described below; unsupported operations fail rather than return empty successes. In a disk-only connection there are no open documents to list; use `files/list` to discover paths and `documents/read` to read them.

Stream mode continues after ordinary request errors; its exit status describes the transport. One-shot request failures exit 65. Usage errors exit 64, stream I/O errors exit 74, and oversized stream frames terminate with a structured limit error and exit 65. Responses use stdout and startup/transport diagnostics use stderr.

## Explicit live connection

Select a workspace folder and run `:agent api start` in the editor. `:agent api status` reports the connection descriptor path; `:agent api stop` revokes the listener and clients and removes its owned descriptor. Start/stop filesystem work runs in workers; there is no automatic start or reconnect. Closing the editor also revokes its source and owned connections.

Connect from a terminal with `shed --workspace-api --root <same-directory> --connect <descriptor-path> --stdio`, or use `--request '<JSON>'`. The CLI remains headless. Queries use the live buffer adapter, including unsaved contents and stable document revisions. A tab/Explorer switch cannot retarget the connection. Multiple editor instances have separate descriptors and random instance IDs; connecting requires the matching canonical root, instance and 256-bit token.

The server binds only IPv4 loopback on an ephemeral port. The descriptor contains a credential, is never printed as content, and must remain in its owner-only session directory (POSIX permissions or owner-only ACL). Unsupported permission models, symbolic descriptor links, shared permissions, invalid descriptors and a mismatched root fail closed. Credential storage must be outside the exposed workspace, so an API cannot reveal its own credentials through document reads. Configure a session directory outside the selected root when working on a folder that would contain it.

Eight simultaneous clients are allowed. Authentication has a three-second absolute deadline and a 4 KiB frame limit. Authenticated frames have a sixty-second socket deadline, 1 MiB requests and 16 MiB responses; the CLI has a thirty-second response timeout. Malformed JSON/UTF-8 produces structured errors; oversized frames abort that connection. Valid notifications produce no response and do not desynchronize later requests. This is a local workspace API, not ACP/MCP, a remote service, an external-process sandbox, or a background agent runtime. The default connection is read-only; proposal mode is explicitly enabled as described below. Unsupported operations remain explicit errors.

## Common resource transaction

LSP workspace edits now use the controller-free `WorkspaceEditTransaction` for staging, replacement, rename, deletion, commit and rollback. Staged files are forced to disk and replacements reuse the ordinary save path's metadata-copy policy. The former duplicate controller transaction and unused direct-write helpers are removed. Version/workspace preflight and the thread affinity of editor callbacks remain responsibilities of the caller; this extraction is not a complete agent edit service.

Transactions fingerprint resources, including directory trees bounded to 10,000 descendants, without following symbolic links. Rollback checks for newer content before removing a replacement or reversing a rename. An external writer holding a backed-up original invalidates commit; rollback preserves that writer's newer data. Undo callbacks continue after an I/O/runtime failure and return `RECOVERY_REQUIRED`, failure details and retained recovery paths. Cleanup removes only owned staged resources and known backup entries, preserves foreign additions, and reports failures. LSP result messages include those recovery notices instead of silently swallowing rollback failures. Filesystem identity/hash checks are preconditions and recovery safeguards, not operating-system locking or a sandbox against independent writers.

## Shared text changes and encoding

`WorkspaceTextEdits` supplies bounded line-based hunks, selected-hunk application and conservative three-way rebasing. Hunk offsets stay on grapheme boundaries. Rebasing refuses overlapping intervening changes; unrelated later human edits survive an inverse patch. The diff bounds its line list and dynamic-programming matrix, merging large/complex regions into a coarse hunk rather than allocating an unbounded matrix. Review UI and durable task undo still need to consume these primitives.

`TextFileCodec` now owns strict Unicode/BOM encoding and the explicit Latin-1 compatibility path used by ordinary editor loads. Workspace reads retain their stricter UTF-8/BOM-marked UTF-16 boundary. Editor saves, asynchronous saves and backups preserve mixed newline bytes in unchanged spans; changed/inserted spans use an adjacent newline style. An explicit newline setting normalizes the file and remains dirty if selected while an older asynchronous save is in flight. Save images retain their selected encoding instead of guessing it from written bytes.

Closed-file LSP edits use this codec and normalized offsets, retain source format through rename-and-edit, and check captured disk versions before staging. Resource-only binary renames do not require text decoding. These paths are tested directly through a disk-only LSP controller without constructing a frame. ## Durable text proposals and transport

`:agent api start propose` explicitly starts a connection with READ and PROPOSE capabilities. The default start remains read-only. Changing mode requires stopping the existing connection. Neither connection grants APPLY. Trusted actor identity comes from the adapter, never a request field. Current local API connections share the `workspace-api` actor within a workspace; request IDs should therefore be globally unique for those clients. These tokens authenticate a local connection, not separate provider identities.

Connected `workspace/info` advertises permitted proposal operations. `proposals/propose` requires workspaceId, requestId, taskId, turnId and changes. Default text changes contain document, expectedVersion and normalized-LF text; explicit create/delete/rename changes use the contracts below. Existing complete text documents, including unsaved editor buffers, are supported. Empty replacement text is valid. Creating a proposal does not modify the workspace. Repeated identical actor/request IDs return the persisted outcome; different payloads with the same ID conflict. Task/turn strings are provenance labels at this stage, not implemented task/session lifecycle objects.

`proposals/list` provides bounded pages with nextOffset/truncated. `proposals/read` accepts id, document index, optional expectedRevision, text variant (before/proposed/selected), UTF-16 offset/limit and hunkOffset/hunkLimit. Text pages preserve graphemes; hunk pages contain ranges, replacement lengths and selection state. `proposals/revise` requires the reviewed revision and can edit text or select hunk indices; `proposals/reject` requires the reviewed revision. Apply/undo/rebase are implemented by the shared reviewer service and permission-gated in the transport; proposal-only clients cannot invoke them.

Private history lives outside the exposed workspace under the owner-only session directory at agent-workspace/<workspaceId>. Immutable chained events and exact UTF-16/raw-byte blobs preserve original contents, actor, constraints, review revision and application outcomes. An OS file lease and in-process lease guard prevent concurrent journal mutations. Interrupted applying/undoing records require inspection; they never silently retry. Recovery inspection and resource intent tracing are implemented below. Guarded text restoration is implemented below. General resource recovery and durable task/session lifecycles remain pending.

Application validates all source versions/formats before effects, uses the shared filesystem transaction, and applies live text as an atomic EDT batch with native undo grouping. Rejected/rolled-back batches do not pollute native undo history. Raw document edits invalidate versions even if the text later returns to its prior value. Cancelling a queued EDT edit prevents it running later; once it starts, its actual result is recorded. Open buffers remain unsaved and the result explicitly records pendingSaveAtApplication. Closed files retain their encoding/BOM and mixed newline spans. Explicit rebasing and inverse changes preserve disjoint human edits; overlapping changes conflict. The broader LSP/project-replace migration, general binary/directory operations and task-level review are still required.

## Resource intent tracing

The common transaction now publishes resource intents before backup, replacement, rename or parent-directory creation. Staged content is forced before its identity/digest is recorded. Proposal journals persist each intent before allowing the corresponding move, including exact staging/backup paths and resource fingerprints. An observer/journal failure prevents that step; prior steps use the existing guarded rollback. Undo retains the original application record separately, so interrupted undo does not erase the evidence needed to explain the accepted change.

A headless child-process fixture halts abruptly after backup and before replacement, without running cleanup. The parent reopens the private journal, locates the recorded original and staged file, and verifies their bytes/digests. Focused transaction, proposal, transport, review, LSP-format and architecture checks pass. This demonstrates process-interruption evidence retention; it does not yet provide automatic recovery for every mixed resource operation or establish power-loss guarantees.

Resource transactions also accept reviewed resource identities for replacement, rename and deletion, and recheck originals after intent persistence. New regular files use an explicit absent-target creation operation: publishing a hard link to staged bytes fails atomically if another writer has occupied the destination. Filesystems without hard-link support fail explicitly; creation never falls back to an overwriting move. The temporary link is removed after publication. Headless tests cover concurrent target creation during journaling, stale source/destination identities, changes while an intent is recorded, and normal create/rollback/cleanup. These checks are app-level concurrency guards, not filesystem isolation against arbitrary external processes.

## Recovery inspection and reconciliation

For an interrupted proposal, Inspect recovery compares each recorded operation's before/after contents with the current workspace. Disk-backed effects additionally compare exact raw bytes, so matching normalized text with changed newline/BOM bytes is not treated as an exact outcome. Missing, partial, diverged and unreadable documents are explicit. Both text and raw preimages are integrity-checked before a result can be verified. Recorded staging/backup intents are displayed; listed paths may already have been cleaned up.

Record verified outcome changes history only. It requires APPLY permission, the inspected journal revision, the evidence fingerprint and the original protected-path constraints. Any intervening version/content change invalidates the inspection. Entirely applied operations become APPLIED/UNDONE; entirely unapplied operations become FAILED or restore the prior APPLIED state for an interrupted undo. Retries are idempotent. Reconciliation never rewrites files, mutates buffers or removes recovery artifacts. Mixed or missing results remain unresolved and cannot be labeled complete through this action; guarded text restoration is available as described below; general file-operation recovery remains required work.

The same contract is available as proposals/recovery and proposals/reconcile. Proposal-only clients can inspect evidence but cannot reconcile it. The human panel presents the evidence in its Recovery tab and enables reconciliation only for an interrupted operation with a verified outcome. Service, transport and headless component checks cover unchanged files on reconciliation, stale inspections, partial/missing effects, raw-format differences, corrupt preimages, interrupted undo followed by another undo, and the actual human controls.

## Reviewed file deletion

A deletion change is `{"kind":"delete","document":"src/old.txt","expectedVersion":"<reviewed document version>"}`. It rejects replacement text and hunk revisions: deletion is a whole-file decision. It can be combined with text and creation changes in one approved transaction. This currently covers complete regular text files within the proposal limits; binary resources and directory operations remain pending. A scratch buffer cannot be deleted as a disk file. Paths are resolved to the canonical resources shown in review, with the same protected/excluded-path and capability checks as other edits.

Deletion captures both the editor snapshot and the saved file's bytes, version and filesystem identity. An unchanged unsaved buffer does not hide an intervening disk edit: application refuses either stale snapshot, and explicit rebase captures the new evidence for review. The panel labels the operation Delete, shows the saved disk contents, disables text/hunk editing for the operation, and provides a separate Preserved draft tab for an open document. The API exposes those snapshots through `proposals/read` with `text:"before"` and `text:"draft"` respectively. The draft variant is available only when an editor draft was captured.

Application moves the original into an owner-only directory beneath the private journal's `retained` directory, outside the workspace. This preserves its inode, encoding, newline/BOM bytes, permissions and native file metadata without leaving untracked recovery files in the project. Open editor contents are detached into explicitly unsaved buffers; their text, format preferences and document identities survive. Application and undo remain separate APPLY actions; a proposal-only connection cannot approve either.

Undo requires an absent destination and the intact recorded original. It moves that original back, and rebinds the still-detached original editor buffer while preserving later human edits. A buffer saved elsewhere by the human retains its new binding. An occupied destination, changed original, stale editor version or newly protected path prevents mutation. History and the original must be on the same filesystem for these identity-preserving moves; unsupported cross-filesystem deletion/undo is refused explicitly rather than copying with weaker metadata guarantees.

Interruption evidence records both resource locations. Inspection and restoration distinguish an intact private original, an already-restored workspace file, and mixed editor bindings. Rolling back an interrupted deletion undo returns the original to its private recorded location, so a later undo remains possible. Private retention paths are shape-checked, owner-checked and never recreated by read-only inspection. Retention is bounded to 1,024 resource directories and 512 MiB; automatic pruning, including empty directories after undo, remains part of pending durable-session/history management.

## Bounded file discovery and text search

`files/list` and `search/text` require the connection's workspaceId and READ permission. Both run through the same disk-only CLI or authenticated live bridge, without selecting documents, saving buffers, creating an index, starting Git or opening a window. A request captures editor snapshots once; file-backed unsaved documents override their disk contents, including newly created files. Workspace identities and path policy are checked before reading source contents. Matching an excluded/protected directory also guards its descendants; include filters and includeIgnored never override access policy.

Both methods accept `include` and `exclude` root-relative comma-separated globs, `includeIgnored` (default false), `scope` (`workspace`, the default, or `open`) and `timeoutMillis` (1–10,000, default 5,000). Globs retain the human Search/Replace syntax, including brace alternatives and root matching for `**/`; text and glob matching share cancellation/backtracking guards. Ordinary source queries remain bounded even when a pattern is complex. Cancellation at the service boundary or thread interruption returns CANCELLED; a wire cancellation operation is still pending.

Discovery reads nested workspace `.gitignore` files in-process using JGit's ignore matcher, including negation, anchored/directory patterns, escapes and `**`. Ignored parents remain pruned. Unsaved open `.gitignore` snapshots are used. Unreadable, partial or oversized rule files hide the affected subtree and report IGNORE_UNAVAILABLE instead of silently exposing its contents. Rule files are limited to 256 KiB, individual lines to 4,096 characters and total lines to 16,384 per request. `includeIgnored=true` explicitly bypasses these discovery rules, while path policy still applies. This mode intentionally does not open a Git repository, read its index or administrative/global configuration, or inherit UI-only imported search preferences: responses identify `ignoreMode` and `globalGitConfigurationApplied=false`. These are workspace-file discovery rules, not a claim to reproduce every Git configuration source. [Git ignore semantics](https://git-scm.com/docs/gitignore), [JGit project](https://projects.eclipse.org/projects/technology.jgit).

`files/list` accepts `offset` and `limit` (default 200, maximum 1,000). It returns sorted root-relative file paths, URIs, known disk size/mtime and open-document identity/version/dirty state when available. Scratch documents remain in documents/list. `listingVersion` fingerprints the observed listing metadata and filters, not every file's contents. Pass `expectedListingVersion` on subsequent pages to reject changed membership or metadata. `nextOffset` is null when there are no further observed entries. `scanComplete`, `totalKnown` and nullable `total` distinguish a fully scanned listing from a bounded prefix; a complete scan can still have a truncated page.

`search/text` requires a nonempty single-line `query`; whitespace is significant. It accepts `caseSensitive` (default true), `regex` and `wholeWord` (both default false), matching the editor's Unicode-word rules. Matching is line-oriented, including for normalized UTF-16/BOM disk text. Each match names the document and exact snapshot version, source (EDITOR/DISK), dirty state, zero-based UTF-16 start/end offsets and one-based line/column/endColumn. Previews are bounded to complete graphemes and carry previewStartOffset/previewTruncated. Scratch documents are included when path filters are empty. A partial editor projection is reported and skipped; the search never substitutes older disk text for it.

Search limits are `limit` (default 200, maximum 1,000 matches), `maxFiles` (default 10,000, maximum 100,000), and `maxFileBytes` (default 2 MiB, maximum 25 MiB; also the per-document UTF-16-character limit for editor text). Shared limits include 100,000 visited directory entries, depth 64, 8 MiB of visited path characters, 32 MiB of captured text characters and 768 KiB of encoded result characters. Disk reads, traversal and matching check cooperative cancellation/deadlines; filesystem calls are not forcibly interruptible. `complete=false`, `truncated` and `incompleteReasons` distinguish result/file/size/time/pattern limits and unavailable contents from an exhaustive no-match result. An exact match limit is complete unless an additional match or another incomplete condition is observed. Queries provide per-document snapshots, not an atomic snapshot of the whole filesystem.

The following requests use the workspace identity returned by workspace/info:

```json
{"jsonrpc":"2.0","id":2,"method":"files/list","params":{"workspaceId":"<workspaceId>","include":"src/**","limit":100}}
{"jsonrpc":"2.0","id":3,"method":"search/text","params":{"workspaceId":"<workspaceId>","query":"WorkspaceDocument","wholeWord":true,"include":"**/*.java"}}
```

## Reviewed file rename

A rename change is `{"kind":"rename","document":"src/old.txt","expectedVersion":"<reviewed document version>","destination":"src/new.txt"}`. Both paths are subject to current and recorded protected/excluded-path constraints. The destination must be absent on disk and in the editor registry. Rename rejects replacement text and hunk revisions; the review panel shows the old and new paths, the unchanged saved contents, and a separate preserved editor draft. Rebase explicitly refreshes source and disk evidence for another review.

Rename can be combined with disjoint text/create/delete operations in one transaction. Paths cannot overlap, contain one another, form rename chains, or overwrite existing resources. It preserves the original file's bytes, inode and metadata by atomically claiming an absent destination with a hard link before unlinking the source. Both paths must be on the same filesystem with hard-link support. No copying or overwriting fallback weakens that contract. This currently covers complete regular text files within proposal limits; general binary/directory operations remain pending.

An open buffer follows the file without saving its draft, retaining document identity and participating in the existing atomic editor batch and LSP binding synchronization. Binding into a different configured workspace is refused and rolled back; changing configured roots during editor preflight requires a retry. Undo moves the current file back and preserves later edits, including ordinary atomic saves made by the original still-open editor. A captured saved-disk ownership proof distinguishes those saves from unrelated external replacements. An occupied old path or unproven replacement conflicts. An external atomic replacement, or a save after closing and reopening the original buffer, can require a separately reviewed inverse rename; file-key continuity is accepted for in-place changes.

Recovery inspects both names, their recorded identities, and the editor binding. Exact before/after outcomes can be reconciled without rewriting files. Mixed bindings can be restored atomically with filesystem recovery. An interrupted link/unlink stage is restorable only when the paths still alias the unchanged original and a durable post-link intent establishes ownership. A crash before that intent, changed contents, an independent replacement, multiple editor bindings or an editor retargeted elsewhere requires further inspection. Recovery itself records reverse-rename intents so interruption during restoration remains inspectable.

## ACP connection and session service

The controller-independent ACP client uses version 1 and newline-delimited UTF-8 JSON-RPC. It launches only an explicitly supplied executable/argument list in the captured canonical workspace, subject to START_AGENT. There is no implicit shell, automatic provider discovery, network connection or agent startup. Provider configuration resolves `agent.<name>.command`, optional `.args`, `.startup.timeout.ms` (default 15 seconds), and `.turn.timeout.ms` (default 10 minutes). Ordinary project configuration does not grant permission to override those process settings. The Agents workbench consumes this service; these settings alone do not launch an agent.

The connection bounds frames to 1 MiB, pending requests in each direction to 32, outgoing messages to 64, ordered event delivery to 128, and retained stderr to 65,536 characters. Peer callbacks run away from the reader. A permission request can remain pending while unrelated replies, streaming updates and cancellation continue. Structured peer errors retain their numeric code/data. Invalid UTF-8, malformed/oversized frames, unknown/duplicate replies, transport failures and request deadlines stop the connection and fail outstanding work rather than reporting a successful turn. Standard error is captured separately and is never parsed as protocol data.

The session service negotiates before creating a session, advertises only implemented capabilities, retains streamed updates with explicit session IDs, and distinguishes normal completion from refusal, limits and cancellation. Its current display history is bounded to 1,000 events and 2 MiB of payload characters, with an explicit dropped-event count; this is not the durable task history required by item 7. `session/load` is called only when the agent advertises loadSession. Background policy defers protocol-driven authentication that may open a browser or other foreground surface. Unsupported authentication types are reported rather than reproduced in an unowned terminal.

READ-backed `fs/read_text_file` uses the shared workspace query service, so unsaved buffers, exclusions, complete-document checks and workspace boundaries are preserved. Reads support ACP's one-based line selection and reject responses over 65,536 characters instead of silently truncating a file. File writes are advertised only when the connection has a proposal store and READ/PROPOSE capability. They use the reviewed-write flow below; saving a proposal does not fulfill the ACP write-success contract. Terminal operations remain unadvertised.

Permission requests preserve the peer's tool/option identities. A selected allow-once option must also satisfy the existing capability/path policy; persistent allow grants remain unavailable until durable task policy exists. Cancelling a prompt immediately resolves pending permission requests with the ACP cancelled outcome and sends session/cancel. Updates remain consumable until the agent finishes the original request. If the agent fails to acknowledge cancellation within five seconds, the owned connection is stopped and the outcome is reported as failed/uncertain, not successful cancellation. The process and observed descendants with matching process-start identities are terminated on close; this is lifecycle management, not containment of arbitrary external executables or unobserved detached descendants.

## Reviewed ACP file writes

`fs/write_text_file` is available only during an active prompt on a connection with reviewed writes enabled. It captures the canonical target and current workspace snapshot, then submits one text or creation proposal through `WorkspaceProposalService`. It uses the same path policy, actor/request identity, version checks, private journal, format preservation, review, undo and recovery machinery as other proposals. Existing files are never written directly by the ACP adapter. Missing files use an absence precondition; directories and binary content remain outside the text proposal contract. Text is normalized to logical LF newlines, matching workspace reads; existing disk encoding, BOM and newline spans remain preserved by the common transaction.

The RPC stays pending until a committed review outcome is observed. Exact accepted text returns the ACP empty success result. Rejection returns an error. If the human edits the proposal, selects only some hunks, or rebases it to different text, the accepted changes remain applied but ACP receives `REVIEW_CHANGED_CONTENT` and must read again. A recorded application to an open editor buffer counts as a logical file update and remains unsaved; the transcript marks that distinction. A proposal by itself, an interrupted transaction, a failed application, or an undone change cannot produce a successful write response.

The adapter holds at most 32 pending writes. Its background workers observe the shared journal, including decisions made by another reviewer instance. Journal contention is explicitly retryable. Review controls retry brief contention in the background while retaining their captured proposal and revision. Cancellation, session closure and premature turn completion request withdrawal of outstanding proposals. Owner withdrawal and human application serialize under the same cross-process journal lease. Withdrawal rejects the latest still-pending or failed revision, including revisions edited by a reviewer. If application already won, its actual outcome remains recorded; cancellation never silently rolls it back. A new prompt cannot start while preceding write cleanup is pending, even if an agent acknowledges cancellation early. Incomplete storage cleanup produces an explicit review-required event. Host-crash recovery and durable task/provider resumption still belong to the unfinished durable-session requirement.

The conversation displays pending file review and an explicit Review changes button. The button opens the matching proposal directly, including proposals outside the currently loaded page. Existing unsaved review edits are preserved until the human saves or discards them. Incoming writes never select a tab or open a window. Workspace and proposal-store paths are captured together at connection time. External agent tool permissions remain separate: enabling reviewed client writes does not grant APPLY, command execution or unrestricted external edit-tool approval. Shed's capability checks do not sandbox the external agent's own operating-system access.
