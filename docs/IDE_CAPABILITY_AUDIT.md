# IDE capability audit

This is a repository audit, not marketing copy. It compares the checked-in implementation with current official VS Code and Zed documentation as consulted on 2026-09-05. It does not count a protocol client, an extension interface, or a command wrapper as turnkey feature parity.

## Bottom line

Shed is a local, extensible code editor/workbench with substantial IDE capabilities. It is reasonable to describe it as an **IDE workbench** if the claim names its local and extension-driven nature. It is not accurate to describe it as feature-parity with VS Code or Zed, nor as a fully featured remote IDE.

VS Code's extension platform covers declarative language metadata, programmatic language features, debugging, SCM, workbench UI, configuration, keybindings, themes, publishing, and multiple extension hosts. [VS Code Extension API](https://code.visualstudio.com/api), [capability overview](https://code.visualstudio.com/api/extension-capabilities/overview), and [extension hosts](https://code.visualstudio.com/api/advanced-topics/extension-host). Zed language extensions require Tree-sitter grammar metadata and queries, and may add language servers; it also has an extension gallery. [Zed language extensions](https://zed.dev/docs/extensions/languages), [Zed extensions](https://zed.dev/docs/extensions), and [extension installation](https://zed.dev/docs/extensions/installing-extensions).

## What the code currently does

### Language profiles

`LanguageProfile` makes a Java extension language visible in the status bar and supplies bounded, literal lexical tokens to the highlighter and comment actions. It can also apply a language-local tab width and tabs-versus-spaces choice to editing and LSP formatting, without changing global user settings. It intentionally does not accept arbitrary regular expressions. This adds real editor behavior beyond LSP process selection.

It still does **not** add TextMate grammars, Tree-sitter parsing, extension-defined grammar/query injections, language-specific folding, semantic-token production, or formatter registration. Built-in lexical highlighting does inject JavaScript/CSS in HTML and known languages in Markdown fences, but that is not a structural grammar platform. The official Tree-sitter Java binding currently requires JDK 22+, whereas Shed's supported runtime is JDK 21, so it is not an appropriate runtime dependency here. [Tree-sitter Java binding](https://tree-sitter.github.io/)

For Java specifically, the local symbol fallback now uses the JDK compiler parser with annotation processing disabled. It extracts recovered declarations from the in-memory buffer for the document-symbol picker, breadcrumbs, and explicit local workspace-symbol fallback, including while the document contains syntax errors. It does not resolve types, read a project classpath, run annotation processors, compile source, supply AST highlighting/folding, or replace a configured Java LSP. `:language` retargets an LSP only when the same extension explicitly registered a matching `LanguageContribution`; LSP behavior remains limited to what the server and Shed's existing LSP client expose.

Outside profiles, Shed loads user `.json` and `.code-snippets` files using a bounded VS Code-compatible snippet subset; local Java extensions can register bounded snippets scoped to the selected profile or LSP language id. It supplies a parser-backed Java declaration fallback plus cautious regular-language local outlines for Kotlin, C#, PHP, Ruby, Swift, Python, JavaScript/TypeScript, Go, Rust, C/C++, YAML, TOML, SQL, and shell files. `:workspace symbols <query>` uses those outlines only as an explicit, ignored-filtered, 2 MiB-per-file/300-result local fallback when no usable LSP workspace-symbol result exists; it does not create a background index or structural project model. Shed can render semantic tokens only when an already configured language server provides them. Kotlin LSP, csharp-ls, Intelephense, Ruby LSP, and SourceKit-LSP now have direct launch paths when the user has installed them; they are neither bundled nor managed downloads, and each remains subject to its upstream toolchain and project requirements. Those are useful editor features, but they do not create a structural grammar or a broad language-extension ecosystem.

### Debugging

Shed has real local Python and Go launch paths when the user has installed upstream `debugpy-adapter` or `dlv`: an explicit start can choose `python-debugpy` for the active `.py`/`.pyw` file or `go-delve` for the active `.go` file when nothing is selected. The Go path starts `dlv dap --listen=127.0.0.1:0`, accepts only its announced loopback endpoint, and sends Delve’s `mode: "debug"` launch setting; it is not remote TCP support. Shed also supplies user-installed `netcoredbg --interpreter=vscode`, `lldb-dap`, and `gdb --interpreter=dap` adapters for explicit C#/.NET and compiled native configurations, or compatible imported `coreclr` and `lldb-dap` launch configurations. It deliberately does not treat `.cs`, C/C++, or Rust source files as launch artifacts, and does not translate CodeLLDB or `cppdbg` settings; GDB DAP also requires an upstream GDB build with Python support. All paths run an explicitly configured local pre-launch workspace task before opening the adapter, then perform DAP initialization, persisted source and named function-breakpoint synchronization (including enabled conditional and hit-count fields where declared and advertised; source breakpoints also support log points), adapter-filter exception-breakpoint enable/disable, `configurationDone` when supported, stopped-frame inspection, opt-out automatic navigation to an existing local selected frame source, watch evaluation, and explicit Continue/Next/Step In/Out/Pause controls. The built-in Go Delve, LLDB, and GDB declarations include only capabilities verified from their DAP support, and a session does not send them without the corresponding initialize response. Other debugger adapters remain user-configured or extension-contributed; function breakpoints and rich source breakpoint fields require both local configuration and the matching capability advertised at DAP initialization, while execution controls require a local declaration.

It can inspect a bounded, strict `.vscode/launch.json` subset and, after an explicit `.code-workspace` import whose folders still match, its `launch` object; compatible profiles still require an already configured adapter. It accepts only a bounded launch-only `env` object with portable names and direct single-line string values, then passes it to the adapter without modifying the host process; it rejects `null` unsets and VS Code variable expansion in those values. It does not discover an adapter from the current language or project, import VS Code debugger extensions, translate adapter-specific options, consoles, compounds, arbitrary variables, or persist an imported profile. The sole task-label bridge maps a `preLaunchTask` only when its exact label resolves uniquely to an accepted session-local process or POSIX-shell task across the compatible folder and workspace sources; its accepted sequential prerequisites run first, while provider, parallel, ambiguous, and otherwise unsupported tasks do not resolve. An explicit `.shedtests` mapping may also select an accepted `vscode:<name>` profile for a test and supply bounded `${testFile}`/`${testId}` expansion; ordinary debug starts reject those placeholders. It does not manage Python environments, provide turnkey test-framework debugger setups, offer adapter-specific exception conditions/options beyond per-filter enable/disable, navigate to a missing source, support reverse execution, or offer remote TCP/debug-host placement. Remote debugging is an explicit stdio bridge for a configured already-installed adapter and maps only declared workspace paths. Run to Cursor is available only through the standard DAP `gotoTargets`/`goto` flow after both local declaration and runtime capability confirmation; it is not enabled for the built-in Python profile without that confirmation. `.shedtests` can explicitly map a discovered test selection to a user-provided DAP configuration, but Shed does not infer that mapping or debugger arguments. Zed documents automatic scenarios for Rust, Go, Python, JavaScript, and TypeScript, pre-debug build tasks, and richer exception-breakpoint management; Shed should not claim comparable debugger coverage. [Zed debugger](https://zed.dev/docs/debugger)

### Tasks

Shed can inspect a bounded, non-symlink `.vscode/tasks.json` as JSONC and, after an explicit matching-folder `.code-workspace` import, its `tasks` object, then expose compatible `process` tasks and, on a POSIX host, compatible `shell` tasks for the session. Process command and arguments remain direct argv. A shell task with arguments keeps each value distinct through expansion then POSIX strong quoting; a shell task without arguments retains its one raw shell command. It permits only the existing workspace/file placeholders, bounded cwd/environment, exact single `$tsc`, `$eslint-compact`, `$eslint-stylish`, `$msCompile`, `$go`, or `$gcc` matchers (or no matcher), and the two directly mappable presentation states. The supported parsers retain error/warning severity for the Problems view. It neither writes a Shed or VS Code task file nor executes on import. A task must still be named explicitly through `:task run` or `:task dry-run`, then faces the same workspace containment, remote-session, and Dev Container validation as a native direct task. An accepted task's exact label may additionally be used by an accepted compatible launch profile's explicit `preLaunchTask` only when it is unique across sources; that debug start still executes no other task automatically.

This accepts only label-based `dependsOn` with explicit sequential order. It does not import task-provider types, detected tool tasks, `dependsOn` object forms, default or parallel/compound execution, background/watch state, `runOn`, inputs, groups/default builds, operating-system overrides, shell selection/quoting overrides, custom/modified/multiple problem matchers, or terminal panel behavior. `$tsc-watch` remains rejected because it relies on background-task readiness state. VS Code documents all of those task-system capabilities; Zed documents task and runnable workflows but not a portable `tasks.json` equivalent. This bridge closes a common project-onboarding gap but should not be presented as VS Code or Zed task parity. [VS Code tasks](https://code.visualstudio.com/docs/debugtest/tasks), [Zed running and testing](https://zed.dev/docs/running-testing)

### Remote commands

`:remote exec <id> <command...>` is direct argv at Shed's boundary. SSH execution safely quotes the remote POSIX command and changes to the URI path; Docker uses `docker exec --workdir`; WSL uses `wsl.exe --cd`; a Git connection executes in its local clone. Results are capped and shown in a scratch buffer.

This does not relocate LSP, test discovery, debugging, extension code, or file watching by default. A selected Tests root under a connected SSH, container, or WSL workspace does explicitly run dynamic discovery and tests through that remote provider, maps paths to the local mirror, and retrieves only declared reports into a private cache; static Java and unittest discovery remains a local-mirror scan. A selected local Dev Container root likewise runs explicit dynamic tests through `devcontainer exec`, but only in an already-running container and only with a generated mounted report cache that is parsed and removed locally. A configured `.shedtests` test-debug mapping can explicitly start an already-installed remote stdio DAP adapter, but Shed never infers a mapping, adapter, or arguments. A globally enabled, explicitly user-configured `lsp.<ext>.command` may run through an SSH, container, or WSL workspace, or an already running local Dev Container after a runtime-root probe, and receives translated remote-root `file:` URIs; it has no remote installer, host bootstrap, persistence/reconnect mechanism, or remote extension host. `:remote terminal` is an explicitly selected PTY bridge. `:remote use` creates a separate in-memory `RemoteWorkspaceSessionService` selection: ordinary terminals and `:task run` beneath that local mirror use the provider until `:remote unuse`, close, or exit, but the editor remains local. `:remote forward` is a separately explicit `SshPortForwardService` process that listens only on `127.0.0.1`; it has no discovery, persistence, public binding, or automatic tool integration. Normal terminals and tasks otherwise remain local; an explicitly connected local Dev Container supplies the other session-only routing option. A task can always be explicitly targeted with `:task remote`; it carries either direct argv or a bounded POSIX shell command, plus workspace-relative cwd and declared environment. SSH remains a remote shell boundary; command execution has the permissions of the selected remote account or container. This remains materially different from VS Code and Zed remote servers, which host core project tooling remotely.

### Terminal integration

The host creates per-terminal startup files under `~/.shed/shell-integration/`. Bash, Zsh, Fish, Windows PowerShell, and PowerShell 7 can emit command-start, command-finish, and current-directory events. The Fish path uses an isolated `XDG_CONFIG_HOME` and sources an existing Fish `config.fish` when present. PowerShell starts `-NoProfile`, sources only its current-user profiles in normal order from the per-terminal bootstrap, and then loads Shed's hook; it preserves custom PSReadLine Enter bindings by falling back to an event from command history after execution. Shed does not modify the user's shell startup files.

Events are retained only in memory and may contain sensitive command text. They are metadata, not an execution sandbox or a complete shell-integration protocol.

## Verification boundary

The repository has focused tests for lexical profiles, terminal startup generation, deterministic provider routing, and protocol/model behavior. Those tests do not prove a live SSH host, Docker container, Dev Container CLI, Jupyter kernel, debug adapter, or third-party language server works in every environment. Environment-dependent integrations remain dependent on user-installed tools and their configuration.

## Honest product language

Use: “Shed is a local Java desktop IDE workbench with LSP/DAP foundations, test and source-control tooling, explicit remote workspace bridges, and a typed local extension API.”

Avoid: “Shed is a fully featured VS Code/Zed replacement,” “remote development parity,” “full language support,” “built-in database/deployment/collaboration,” or “Marketplace-compatible extensions.”
