# IDE capability audit

This is a repository audit, not marketing copy. It compares the checked-in implementation with current official VS Code and Zed documentation as consulted on 2026-09-04. It does not count a protocol client, an extension interface, or a command wrapper as turnkey feature parity.

## Bottom line

Shed is a local, extensible code editor/workbench with substantial IDE capabilities. It is reasonable to describe it as an **IDE workbench** if the claim names its local and extension-driven nature. It is not accurate to describe it as feature-parity with VS Code or Zed, nor as a fully featured remote IDE.

VS Code's extension platform covers declarative language metadata, programmatic language features, debugging, SCM, workbench UI, configuration, keybindings, themes, publishing, and multiple extension hosts. [VS Code Extension API](https://code.visualstudio.com/api), [capability overview](https://code.visualstudio.com/api/extension-capabilities/overview), and [extension hosts](https://code.visualstudio.com/api/advanced-topics/extension-host). Zed language extensions require Tree-sitter grammar metadata and queries, and may add language servers; it also has an extension gallery. [Zed language extensions](https://zed.dev/docs/extensions/languages), [Zed extensions](https://zed.dev/docs/extensions), and [extension installation](https://zed.dev/docs/extensions/installing-extensions).

## What the code currently does

### Language profiles

`LanguageProfile` makes a Java extension language visible in the status bar and supplies bounded, literal lexical tokens to the highlighter and comment actions. It can also apply a language-local tab width and tabs-versus-spaces choice to editing and LSP formatting, without changing global user settings. It intentionally does not accept arbitrary regular expressions. This adds real editor behavior beyond LSP process selection.

It still does **not** add TextMate grammars, Tree-sitter parsing, extension-defined grammar/query injections, language-specific folding, semantic-token production, or formatter registration. Built-in lexical highlighting does inject JavaScript/CSS in HTML and known languages in Markdown fences, but that is not a structural grammar platform. `:language` retargets an LSP only when the same extension explicitly registered a matching `LanguageContribution`; LSP behavior remains limited to what the server and Shed's existing LSP client expose.

Outside profiles, Shed loads user `.json` and `.code-snippets` files using a bounded VS Code-compatible snippet subset; local Java extensions can register bounded snippets scoped to the selected profile or LSP language id. It also supplies cautious regular-language local outline fallbacks for Java, Kotlin, C#, PHP, Ruby, Swift, Python, JavaScript/TypeScript, Go, Rust, C/C++, YAML, TOML, SQL, and shell files. `:workspace symbols <query>` uses those outlines only as an explicit, ignored-filtered, 2 MiB-per-file/300-result local fallback when no usable LSP workspace-symbol result exists; it does not create a background index or structural project model. Shed can render semantic tokens only when an already configured language server provides them. Kotlin LSP, csharp-ls, Intelephense, Ruby LSP, and SourceKit-LSP now have direct launch paths when the user has installed them; they are neither bundled nor managed downloads, and each remains subject to its upstream toolchain and project requirements. Those are useful editor features, but they do not create a structural grammar or a broad language-extension ecosystem.

### Debugging

Shed now has a real local Python launch path when the user has installed upstream `debugpy-adapter`: an explicit start can choose its profile for the active `.py` or `.pyw` file when nothing is selected; it runs an explicitly configured local pre-launch workspace task before opening the adapter, then performs DAP initialization, persisted source-breakpoint synchronization (including enabled, conditional, hit-count, and log-point fields), adapter-filter exception-breakpoint enable/disable, `configurationDone` when supported, stopped-frame inspection, opt-out automatic navigation to an existing local selected frame source, watch evaluation, and explicit Continue/Next/Step In/Out/Pause controls. Other debugger adapters remain user-configured or extension-contributed; rich source breakpoint fields require both local configuration and the matching capability advertised at DAP initialization, while execution controls require a local declaration.

It can inspect a bounded, strict `.vscode/launch.json` subset and expose compatible profiles only for an already configured adapter; it does not discover an adapter from the current language or project, import VS Code debugger extensions, translate adapter-specific options, `env`, consoles, compounds, arbitrary variables, or task labels, or persist an imported profile. It does not manage Python environments, provide turnkey test-framework debugger setups, offer adapter-specific exception conditions/options beyond per-filter enable/disable, navigate to a missing source, support reverse execution, or offer remote TCP/debug-host placement. Remote debugging is an explicit stdio bridge for a configured already-installed adapter and maps only declared workspace paths. Run to Cursor is available only through the standard DAP `gotoTargets`/`goto` flow after both local declaration and runtime capability confirmation; it is not enabled for the built-in Python profile without that confirmation. `.shedtests` can explicitly map a discovered test selection to a user-provided DAP configuration, but Shed does not infer that mapping or debugger arguments. Zed documents automatic scenarios for Rust, Go, Python, JavaScript, and TypeScript, pre-debug build tasks, and richer exception-breakpoint management; Shed should not claim comparable debugger coverage. [Zed debugger](https://zed.dev/docs/debugger)

### Tasks

Shed can inspect a bounded, non-symlink `.vscode/tasks.json` as JSONC and expose compatible `process` tasks for the session. It preserves their command and arguments as direct argv, permits only the existing workspace/file placeholders, bounded cwd/environment, no matcher or an empty matcher array, and the two directly mappable presentation states. It neither writes a Shed or VS Code task file nor executes on import. A task must still be named explicitly through `:task run` or `:task dry-run`, then faces the same workspace containment, remote-session, and Dev Container validation as a native direct task.

This does not import `shell` tasks, task-provider types, detected tool tasks, `dependsOn`/compound execution, background/watch state, `runOn`, inputs, groups/default builds, operating-system overrides, custom problem matchers, or terminal panel behavior. VS Code documents all of those task-system capabilities; Zed documents task and runnable workflows but not a portable `tasks.json` equivalent. This bridge closes a common project-onboarding gap but should not be presented as VS Code or Zed task parity. [VS Code tasks](https://code.visualstudio.com/docs/debugtest/tasks), [Zed running and testing](https://zed.dev/docs/running-testing)

### Remote commands

`:remote exec <id> <command...>` is direct argv at Shed's boundary. SSH execution safely quotes the remote POSIX command and changes to the URI path; Docker uses `docker exec --workdir`; WSL uses `wsl.exe --cd`; a Git connection executes in its local clone. Results are capped and shown in a scratch buffer.

This does not relocate LSP, test discovery, debugging, extension code, or file watching by default. A selected Tests root under a connected SSH, container, or WSL workspace does explicitly run dynamic discovery and tests through that remote provider, maps paths to the local mirror, and retrieves only declared reports into a private cache; static Java discovery remains a local-mirror scan. A selected local Dev Container root likewise runs explicit dynamic tests through `devcontainer exec`, but only in an already-running container and only with a generated mounted report cache that is parsed and removed locally. A configured `.shedtests` test-debug mapping can explicitly start an already-installed remote stdio DAP adapter, but Shed never infers a mapping, adapter, or arguments. A globally enabled, explicitly user-configured `lsp.<ext>.command` may run through an SSH, container, or WSL workspace, or an already running local Dev Container after a runtime-root probe, and receives translated remote-root `file:` URIs; it has no remote installer, host bootstrap, persistence/reconnect mechanism, or remote extension host. `:remote terminal` is an explicitly selected PTY bridge. `:remote use` creates a separate in-memory `RemoteWorkspaceSessionService` selection: ordinary terminals and `:task run` beneath that local mirror use the provider until `:remote unuse`, close, or exit, but the editor remains local. `:remote forward` is a separately explicit `SshPortForwardService` process that listens only on `127.0.0.1`; it has no discovery, persistence, public binding, or automatic tool integration. Normal terminals and tasks otherwise remain local; an explicitly connected local Dev Container supplies the other session-only routing option. A task can always be explicitly targeted with `:task remote`; it carries only its direct argv, workspace-relative cwd, and declared environment. SSH remains a remote shell boundary; command execution has the permissions of the selected remote account or container. This remains materially different from VS Code and Zed remote servers, which host core project tooling remotely.

### Terminal integration

The host creates per-terminal startup files under `~/.shed/shell-integration/`. Bash, Zsh, and Fish can emit command-start, command-finish, and current-directory events. The Fish path uses an isolated `XDG_CONFIG_HOME` and sources an existing Fish `config.fish` when present. Shed does not modify the user's shell startup files.

Events are retained only in memory and may contain sensitive command text. They are metadata, not an execution sandbox or a complete shell-integration protocol.

## Verification boundary

The repository has focused tests for lexical profiles, terminal startup generation, deterministic provider routing, and protocol/model behavior. Those tests do not prove a live SSH host, Docker container, Dev Container CLI, Jupyter kernel, debug adapter, or third-party language server works in every environment. Environment-dependent integrations remain dependent on user-installed tools and their configuration.

## Honest product language

Use: “Shed is a local Java desktop IDE workbench with LSP/DAP foundations, test and source-control tooling, explicit remote workspace bridges, and a typed local extension API.”

Avoid: “Shed is a fully featured VS Code/Zed replacement,” “remote development parity,” “full language support,” “built-in database/deployment/collaboration,” or “Marketplace-compatible extensions.”
