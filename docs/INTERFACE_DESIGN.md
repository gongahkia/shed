# Shared workbench interface

The production redesign uses Swing, the existing editor, and Shed's Java application boundaries. The bounded renderer comparison selected Swing; the rejected Compose/duplicate Swing prototypes have been archived. The outcome, implementation sequence, raw measurements and verification limits are recorded in [UI modernization](UI_MODERNIZATION.md). This stage does not introduce a framework or replace editor internals.

## Interaction and styling conventions

WorkbenchHeader gives the active workspace, document path and focus/pane context a stable place above OpenEditorsBar. Find file, Commands, Splits, Tools and Settings have explicit entry points and retain existing keyboard/command semantics. Duplicate document names receive distinguishing parent suffixes. Full paths remain available to hover and accessibility consumers.

Settings have full-width search, categories, Modified only, per-value Reset and inline feedback. Text fields retain Enter/focus-loss save behavior. Invalid drafts remain visible through filtering and can be reset. Friendly titles accompany actual configuration keys, descriptions/defaults and apply behavior. Persistence and runtime application continue through SettingsApplication.

ConfigManager palette roles, EditorUiController, UiZoom, WorkbenchStyle and WorkbenchIcons are the single presentation system. Generic text areas follow interface zoom; explicitly assigned source/code fonts retain their separate ownership. Common targets retain a 40-logical-pixel minimum before scaling; large text can increase their height. Shared semantic intents use contrast-adjusted error/warning/success colors and reapply after theme changes. Invalid settings have a border state, and selected/disabled/focused controls retain distinct static cues. Existing saved theme/font/keymap preferences remain respected.

Short docks use a vertically scrollable ToolViewport with a usable scaled content height. Field/action wrapping still follows available width, and keyboard focus reveals controls through nested viewports. This retains the chosen dock geometry while keeping forms and data rows usable.

Tool output and refresh preserve the reader's place where the underlying selection is unchanged. Task runs started in Tasks keep their completion there even after the dock is hidden; command-originated presentation preferences remain available. Cancellation, nonzero exit, loading, empty/filter-empty results and errors have explicit feedback. Refresh does not request focus. Opening a panel does not run a task, debugger or agent.

Review places proposal-wide Apply and Reject in a full-width footer, with nonwrapping secondary actions in a horizontal scroller. A compact workspace/proposer/document summary stays visible; Details retains complete paths, task/revision and format metadata. The review-view tabs scroll instead of wrapping. Its banner distinguishes pending review, working, local review edits, applied changes and recovery. The same proposal/version/admission/journal rules still control execution; opening review never accepts a proposal. Apply to an open document retains the existing unsaved-buffer policy.

Navigation and tools use the existing outline icons with one stroke treatment and foreground/disabled colors, plus tooltips and accessible names. Frequent interactions have immediate state feedback and no new custom animation. Specialized source, terminal, notebook, preview and Git graph implementations remain in their existing lifecycles and shared appearance paths.

## Full design review

Mode: **full**. Scope: the production workbench navigation, documents/splits/tools, settings, shared feedback, approval review and ordinary dialogs in this stage. Framework: Java 21/Swing. The scope is local production behavior and actual captures, not a Windows/Linux native-input or external-screen-reader certification. Earlier interface-refresh captures in [images/interface](images/interface/gallery.json) are historical context rather than current-build evidence.

| Category | Evidence inspected | Result |

| Typography | WorkbenchHeader, OpenEditorsBar, SettingsEditorDialog, shared font/zoom application, tools and production gallery | One UI font/scale path; readable titles and full-width settings; original editor/code typography retained. Current captures and font diagnostics are archived with the final verification. |
| Surfaces | Header/document/split/dock composition; all eight tools; settings/search/review/confirmation; dark/light, narrow/enlarged and detached windows | Wrapping/scrolling retains access to actions. ## Considered and rejected in this stage

| Candidate | Reason rejected |
| --- | --- |
| Replace Swing with the experimental Compose shell | The bounded comparison did not establish enough benefit to justify its renderer/toolchain/native-runtime costs. Keep the decision evidence and remove the rejected implementation. |
| Rebuild the editor to simplify layout | The document/surface adapters already preserve shared undo, live anchors and specialized surfaces. Workbench improvements do not require another text store. |
| Continue a permanent settings sidebar at every width | It consumed the limited width needed by values and descriptions. Search plus category/modified filters works across the supported sizes. |
| Put every review action into one wrapping primary row | Secondary actions can displace Apply/Reject or consume most of a short dock. Keep the decision pair fixed and make secondary actions scrollable. |
| Animate document/tool/hover transitions | These are frequent interactions; static selection/focus/progress cues communicate state without repeated motion or another timer. |

## Verification and verdict

The Java 21 headless `package` check passed **1,288 tests, zero failures/errors, 97 skips**. The complete `TexteditorSwingIntegrationTest` report passed **92 cases, zero failures/errors, one CMake/CTest/CPack availability skip**; it includes the actual output-font assertion and native document/editor/tool focus transitions. The final packaged artifact matches all 1,287 production class hashes captured from that Swing run. [Verification and scope](performance/ui-stage4/verification.json).

The final packaged gallery passes **38 captures**, zero ordinary-control reachability failures, all eight narrow/enlarged tools and the nested Debug form scroll checks. The four production journeys plus task failure/cancellation pass with **18 captures**, including the populated 210-pixel dock/150% text checks. Actual images were inspected for hierarchy, font scaling, data-row readability, decision reachability and coherent state. [Visual index](images/ui-stage4/INDEX.md). Shared hover/pressed/disabled/selected/loading/empty delegates are exercised through real component models; no custom motion was added, so 10%-speed animation review does not apply.

The unchanged 500,000-line and 100 MiB paged checks pass for both preserved JARs. Desktop measurements do **not** establish a clean performance pass: both revisions miss startup targets, additional edit/ranking tails vary across controls, and the counterbalanced attempt timed out under extreme host load. The isolated rankers return identical lists with similar CPU cost, and a GUI diagnostic reproduced large stalls in the old artifact too; this does not conclusively attribute every tail. Raw failures and methods are retained in [UI modernization](UI_MODERNIZATION.md).

**Verdict: Block stage completion on the open desktop-performance verification gate.** No remaining actionable visual findings are identified in the inspected local states; the original findings above are addressed. This verdict does not reclassify failed performance targets as passes. Unverified checks: reliable desktop performance attribution on a stable host; Windows/Linux native behavior; IME and external readers; the wider font/zoom/multi-monitor matrix. Native Debug-form focus was not observed for every final gallery control, although geometry checks ran and the separate native-focus integration case passed. Final journey Robot injection was disabled; earlier OS-key attempts remain inconclusive.
