# Large-File Baseline Benchmark

`LargeFileBenchmark` is the legacy model/filesystem harness for first and immediate second opens, bounded projection movement, whole-content replacement, and save calls. It does not measure ordinary typing or Swing scrolling/painting. Every iteration copies the input to a temporary file, so the supplied file is read only. The benchmark is local-only and does not send telemetry. For accurately separated local edits, dirty saves, independently verified streamed copies, and Markdown UI measurements, use the opt-in [Markdown baseline harness](MARKDOWN_PERFORMANCE_BASELINE.md).

Build the shaded JAR, generate and verify the deterministic UTF-8 corpus, then run the 1 MiB, 100 MiB, and 1 GiB inputs with the same heap limit and iteration count:

```sh
mvn -B -q -DskipTests package
java -cp target/shed-2.0.0.jar shed.LargeFileFixtureGenerator
java -cp target/shed-2.0.0.jar shed.LargeFileFixtureGenerator --verify
java -Xmx4g -cp target/shed-2.0.0.jar shed.LargeFileBenchmark --iterations 3 .shed-large-file-fixtures/large-1m.txt > .shed-large-file-fixtures/benchmark-1m.txt
java -Xmx4g -cp target/shed-2.0.0.jar shed.LargeFileBenchmark --iterations 3 .shed-large-file-fixtures/large-100m.txt > .shed-large-file-fixtures/benchmark-100m.txt
java -Xmx4g -cp target/shed-2.0.0.jar shed.LargeFileBenchmark --iterations 3 .shed-large-file-fixtures/large-1g.txt > .shed-large-file-fixtures/benchmark-1g.txt
```

`LargeFileFixtureGenerator` writes 1,179,648,000 bytes across the three files, plus `fixtures.manifest`. Its default directory is ignored by Git; use `--output <directory>` to choose another local path. The generated bytes are ASCII and therefore valid UTF-8. `--verify` checks each exact byte count, SHA-256 checksum, and manifest before a benchmark. Do not compare runs with different heap limits, JDKs, storage media, or input bytes.

The retained `coldOpen` key means the first Shed open after per-iteration file preparation; `warmOpen` is the immediate second open of that copy. Neither establishes cold operating-system caches. `scroll` measures one bounded projection move after its initial render and is `UNSUPPORTED` when the input does not select large-file mode. `edit` calls `setContent(getContent() + " ")`, a whole-content replacement, and is `UNSUPPORTED` in current large-file mode. An unmodified read-only large-file `save` returns without writing bytes; its near-zero timing is a clean no-op, not streamed atomic-save throughput. These legacy report keys are retained for compatibility.

Each key/value report records Java and OS environment, input path and bytes, workload, a reproducible command, per-operation state, sample count, median and nearest-rank p95 latency, median and p95 observed heap delta, and every failure. `result.state=PASS` means all available operations completed; `ERROR` means an operation or setup failed. Add `--max-p95-ms <positive>` to set a local p95 limit; a completed report above it is `FAIL`. The command exits `0` for `PASS`, `1` for `FAIL`, and `2` for `ERROR`. `-1` timing or heap fields mean an operation had no successful samples.
