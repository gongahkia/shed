# Network and telemetry boundary

This is a source-level audit of Shed's app-owned outbound-capable paths. Shed has no telemetry collector, analytics endpoint, automatic catalog refresh, plugin marketplace, extension downloader, or remote extension host. Local diagnostics, recovery, workspace indexing, and benchmarks remain on disk.

## Default state

- GitHub review is disabled until `:github consent` persists both its setting and receipt.
- Update metadata is disabled until `:update consent` persists both its setting and receipt plus a configured endpoint and verification key.
- Managed language metadata is bundled. `:lsp manage` requires a fresh approval before `ManagedLanguageSupportService` may download or install a listed runtime.
- Remote connections, Docker and Dev Container commands, browser links, debug transports, terminals, tasks, language servers, and port forwards require an explicit user action. The only recurring remote action is a session-only pull started explicitly with `:remote sync start`.

## App-owned paths

| Path | Authorization and behavior | Data boundary |
| :--- | :--- | :--- |
| OpenCode preset | `OpenCodePreset` supplies `OPENCODE_CONFIG_CONTENT` only to the explicitly selected `opencode` provider. Connect launches the installed CLI; no installation, authentication or automatic update is performed by Shed. | Selected code/context and instructions go to the configured agent/model. The preset asks OpenCode to permit read/search only and return proposals; external executable configuration and OS access remain outside Shed's containment. |
| Explicit AI context | `@file` references respect ignores/access policy and use unsaved snapshots. Configured `#skill` sources and ancestor instruction files are captured and listed in Activity. Absolute skill directories are explicit user configuration, not project overrides. | Complete selected source contents are shared with OpenCode through temporary owner-only snapshots. External skills are read only from configured directories. History results remain bounded in memory; the saved work description persists privately under session storage. |
| Approved AI checks | Ask/search and Run task can request headless commands. Requests shows exact argument arrays, directories, deadlines and the reason; execution requires an explicit Run these commands once action. | Approved programs inherit the account's OS/network access and are not sandboxed. No automatic installs, downloads or commands occur. Output is bounded and supplied to the agent for follow-up; cancellation stops the command and tracked children. Native OpenCode bash/edit tools remain denied. |
| Inline AI completion | `OpenCodeCompletionClient` requires explicit user opt-in (`ai.completion.enabled=true`). It launches the configured OpenCode executable through the existing ACP transport on the first request, in a separate temporary working directory. It uses `agent.opencode.model` or OpenCode's default. There is no direct local-inference client, model installer or local-model endpoint setting. | At most 8,192 UTF-16 units before the caret and 4,096 after it. A dedicated tool-disabled connection gets a fresh conversation for each request, with no file paths or other buffers in its prompt. ACP file reads/writes and permission grants are denied. Replies and deadlines are bounded, cancellation closes the owning completion connection, and suggestions never edit source until Tab. OpenCode owns model-provider communication and retention; its executable/configuration is trusted, not OS-sandboxed. |
| GitHub review | `:github consent` gates every review operation; `:github status` only probes local CLI capability. | The user-installed `gh` CLI owns GitHub requests. |
| Signed update metadata | `UpdateMetadataTransport` runs only after consent. It uses a configured HTTPS endpoint, bounded data, no redirects, and Ed25519 verification before surfacing an update. | Shed sends only the metadata request; it never installs or replaces itself. |
| Markdown preview images | `MarkdownPreviewAssets` fetches only bounded validated HTTPS images after the user explicitly opens a normal Markdown preview and leaves `markdown.preview.remote.images` enabled. | Images are held in a disposable per-preview cache; notebooks remain local-image-only. |
| Managed language install | `ManagedLanguageCatalog` and `ManagedLanguageSupportService` require an explicit reviewed install. | The JDT LS archive or user-installed npm owns the network transfer; Shed sends no workspace or telemetry data. |
| Remote workspace | `:remote open`, reconnect, bootstrap, pull, push, exec, terminal, use, forward, and close are explicit. `:remote sync start` creates only an in-memory recurring pull with a 5–3,600 second interval. `SshPortForwardService` listens only on loopback and stops with the connection or app. | Git, rsync/SSH, Docker, or WSL owns the transport and credentials. URI passwords are rejected; no contributed provider or remote host is loaded. |
| Dev Container CLI | `DevContainerController` exposes explicit build, up, lifecycle, stop, down, connect, exec, terminal, and task commands for a workspace with local `devcontainer.json`; `DevContainerRuntime` owns direct CLI invocation. | The user-installed `devcontainer` CLI owns Docker, registry, and network behavior. |
| Docker workbench | `DockerController` opens a themed local workbench for containers, images, volumes, and networks. `DockerRuntime` starts only direct-argv, cancellable commands selected through that workbench or explicit `:docker` commands. | The user-installed Docker CLI and daemon own engine, registry, image, and network behavior. |
| Docker Compose | Compose actions start only from explicit commands in a workspace with a local Compose file. | The user-installed Docker/Compose CLI owns daemon, registry, image, and network behavior. |
| Notebook | Kernel discovery, selection, execution, and console actions are explicit. | User-installed Jupyter owns kernel/network behavior. |
| Git remotes | Fetch, pull, and push occur only from explicit Git controls. | Git owns the remote protocol. |
| Project file listing | Quick Open runs local `git ls-files` to list tracked and visible untracked files in a repository. | Git reads local index and ignore rules; Shed sends no workspace content. |
| Machine discovery/search | Explicit `files/list` and `search/text` requests read bounded permitted workspace files and unsaved snapshots. JGit is used only as an in-process `.gitignore` parser/matcher; these requests do not instantiate a Git repository, load global Git configuration, or launch Git. | Read-only local filesystem/editor access; no index writes, external process, network request or window. See [agent workspace](AGENT_WORKSPACE.md#bounded-file-discovery-and-text-search) for limits and ignore-source boundaries. |
| Debug adapter TCP | `DebugAdapterTransport` starts from an explicit configured debug session and accepts loopback targets only. | No remote adapter address is accepted. |
| Live workspace API | `WorkspaceBridgeServer` starts only through explicit `:agent api start` and binds IPv4 loopback on an ephemeral port. `WorkspaceBridgeClient` connects only through an explicitly supplied owner-only descriptor and validates the workspace and random instance/token. | The initial API is read-only; authenticated local clients can read permitted saved and unsaved workspace text. No external host, discovery broadcast, provider request or automatic startup occurs. Stop/exit revokes connections; credential storage uses owner-only POSIX permissions or ACLs and fails closed on unsupported filesystems. |
| ACP agent process | `AgentSessionService` requires START_AGENT before `AcpConnection` launches a captured executable/argument list in an explicit workspace. Configuration alone never launches it; ordinary project configuration cannot override provider commands. The Agents panel starts it only on Connect and captures the workspace. Agent-managed sign-in requires foreground opt-in before connecting and a separate Sign in action; it never starts automatically. ACP transport is bounded local stdio, with separate bounded stderr diagnostics. | The configured external agent inherits the user's process environment and OS permissions and may contact its own provider. Prompts and permitted saved/unsaved reads are deliberately supplied to that process. Optional Shed-mediated writes wait for human proposal review; external tool/process permissions remain separate. App-mediated capability/path checks do not sandbox its own filesystem or network access. There is no bundled agent, credential discovery, automatic login or provider download. |
| Agent question browser handoff | `AgentQuestions` advertises URL interactions only with foreground OPEN_UI permission. Every URL requires an explicit Open in browser action after showing its full destination and host; form answers require Submit. | No URL prefetch or page inspection. Only HTTPS and local-development HTTP are accepted, without embedded credentials. Form answers are sent to the requesting agent and are not copied into Shed activity events. Headless tests inject a fake browser handoff. |
| Browser links | Explicit actions delegate a link to the platform browser. | The browser owns resulting requests. |
| User-controlled child processes | Terminals, tasks, configured language servers, formatters, Docker, and Dev Container commands can launch user-selected programs. | Those programs can have their own network behavior; Shed does not inspect or authorize their traffic. |

`gh`, Git, browsers, terminals, tasks, Docker, the Dev Container CLI, and language servers are external programs. Shed can constrain the arguments it gives them, but it cannot verify their implementation or network side effects.

## Regression audit

`NetworkConsentAuditTest` checks the GitHub/update gates and enumerates app-owned direct transport, browser delegation, PTY, and process-launch sources. Add a new transport only with a row here and reviewed consent/default-off coverage.
