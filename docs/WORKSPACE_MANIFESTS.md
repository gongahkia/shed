# Portable Workspace Manifests

Shed can exchange a folder-only multi-root workspace through an explicit manifest:

```text
:workspace export /absolute/path/team.shed-workspace
:workspace import /absolute/path/team.shed-workspace
```

The import command also accepts a standard VS Code `.code-workspace` JSONC file; comments and trailing commas are accepted. Every manifest reads `folders`, where each entry is either a path string or an object with a `path` string. For a standard `.code-workspace` only, a validated object `name` is retained as display metadata in Shed's workspace list and folder manager. It must be a non-empty single line no longer than 120 characters. It never changes the resolved folder identity, containment checks, routing, task/debug working directory, or command behavior. Import itself never runs a command or starts a debugger. [VS Code workspaces](https://code.visualstudio.com/docs/editing/workspaces/workspaces)

For an explicitly imported standard `.code-workspace`, Shed applies a small editor-settings snapshot: `editor.tabSize` (integer `1..16`) and `editor.insertSpaces` (`true`/`false`). It reads those keys from the workspace `settings` object and from each imported folder's local `.vscode/settings.json`; it accepts a single-language override such as `"[java]": {"editor.tabSize": 2}` and a combined block such as `"[javascript][typescript]": {"editor.insertSpaces": true}`. A single-language value takes priority over a combined value in the same scope. For a file under an imported root, Shed applies generic workspace then folder values over its global preference; a matching extension `LanguageProfile` then supplies its language default; matching workspace then folder language overrides take final precedence. This follows the material language-specific-over-generic precedence of VS Code while retaining Shed's smaller configuration model. These values never affect a file outside the imported workspace.

The same snapshot can use `files.exclude` for the Explorer. It accepts at most 100 relative, slash-separated glob keys with a boolean value, including common `**/directory/**` and `**/*.extension` forms. A later matching value in the same object wins; a matching folder value, including `false`, overrides the workspace value. It excludes only Explorer entries under the imported workspace roots. It does not support `when` clauses, absolute/backslash/parent-traversal patterns, file picker filtering, symbols, Git-ignore replacement, or any other VS Code setting.

`search.exclude` accepts the same bounded boolean glob subset and precedence rules, but is intentionally separate: it filters only explicit workspace Search (`:grep`) and Project Replace candidates. It is combined with, never replaces, the existing Git-ignore filter. It does not filter the Explorer, file picker, `:workspace symbols`, terminal, tasks, LSP, or SCM. Every other setting, extension/recommendation, and arbitrary extension data remains inert.

The snapshot is session-only and changes only after `:workspace import` or `:workspace reload`; `:workspace` lists any ignored supported values or unreadable per-folder settings files. It is re-created when a saved session restores the same manifest and exact resolved folder set. It neither writes a VS Code settings file nor watches project configuration, and it does not replicate VS Code's general configuration scopes or language-override precedence beyond this documented subset.

For an explicitly imported standard `.code-workspace` only, Shed also keeps its `tasks` and `launch` objects as a read-only, session-only compatibility source. While the manifest still declares exactly the same resolved folder set, `:task` and `:debug` re-read their existing strict subsets from that source: direct `process` tasks, POSIX `shell` tasks, only explicit sequential unambiguous `dependsOn` labels, and launches that use an adapter already configured in Shed. `${workspaceFolder}` resolves to the deepest configured folder containing the active file (or the selected folder outside one). This is intentionally narrower than VS Code workspace-variable and multi-root behavior. `.shed-workspace` files remain folders-only even if they contain similarly named fields.

The source path can be retained in a saved Shed session, but session restore revalidates the manifest and exact folder membership before exposing its task or launch values. Editing the manifest’s folder list requires another explicit `:workspace import`; no task or debugger starts as a result of that change. See [Workspace Tasks](TASKS.md) and [DAP Architecture](DAP.md) for the accepted fields and rejection rules.

Exports use JSON with `folders` objects and relative paths where possible. They do not synthesize display names. The target must end in `.shed-workspace` or `.code-workspace`; its parent must already exist. An import requires one to one hundred existing local directories, resolves their symbolic links, removes duplicate resolved roots, and replaces the current folder set only after the complete manifest has been validated.

This is distinct from `:workspace save` profiles. Profiles are private Shed session snapshots under the configured session directory and may include buffers and layout. A portable manifest carries folder membership; the constrained `.code-workspace` bridge above is a read-only interoperability input, not a replacement for VS Code workspace settings, task/debug semantics, extension recommendations, virtual filesystems, or remote extension hosts.
